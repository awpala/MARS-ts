# Backend translation plan and oracle evidence

The backend target is a direct translation of the checked-in Java implementation into framework-free TypeScript for MARS-ts 1.0. Preserve existing class names, method names, instruction definitions, algorithms, data tables, error messages, and observable behavior wherever the browser environment permits. This document retains the source analysis and dependency map. The root scaffold is installed and foundational TypeScript classes are being translated under `src/lib/engine/`, with focused Java-generated method probes complementing the CLI corpus. Full assembler/simulator parity remains the P2 exit gate in the [port plan](adrs/0000-port-plan.md).

This is dependency ordering, not permission to implement disconnected pieces ahead of milestones. `InstructionSet`, `ProgramStatement`, assembler, and simulator have mutual type references; translate their contracts together where needed while completing one behavior unit with oracle evidence at a time. Engine modules belong under `/workspace/src/lib/engine/` (`src/lib/engine/` relative to the repository root) and never import UI code. The root `package.json` and configuration files will reference the application under `src/`; there is no separate nested app package. Each module README will identify its Java mapping, state ownership, numerical conventions, and fixtures. The [scope decision](adrs/0002-port-fidelity.md) records the user's direct-translation direction and initial browser substitutions.

## Necessary environment substitutions

Java's `Globals`, register files, memory, coprocessors, random streams, and settings are process-wide. Each browser simulator session must own its own instances while retaining the class responsibilities and method behavior. Shared instruction metadata can be immutable; machine state cannot be shared. Preserve session reset, assembly, run, step, backstep, and stop transitions instead of inventing new execution semantics.

Java `Observable` notices become explicit subscriptions with unsubscribe functions. Preserve the observable access information and order. The UI owns subscriptions and releases them when a view/session closes; the engine never references a component. `SwingWorker` and Swing callbacks require an execution adapter that yields to the browser and can await input, but instruction sequencing, delay slots, breakpoints, and undo records remain `Simulator` and `BackStepper` responsibilities. Worker versus cooperative scheduling remains an implementation decision to record before P2; no scheduler has been selected here.

`SystemIO` and syscall classes receive a host interface for console input/output, source and virtual file access, dialogs, time, and audio. The Node harness and browser supply distinct hosts to the same engine. File selection belongs to the browser UI; the assembler receives the selected source content and names. Dialogs appear within the existing browser view. Neither those adaptations nor SVG conversion belongs inside instruction execution or assembler code.

Java integer wrap, signed versus unsigned comparisons, HI/LO arithmetic, division rounding, and byte order are preserved explicitly. Use normalized 32-bit numbers and exact 64-bit representations, not floating-point multiplication for `long` results. Coprocessor registers retain raw bits; single-precision results round to float precision. Preserve Java's float/double print behavior and `java.util.Random` sequence, including seed treatment and bounded sampling. These are translations of existing behavior, not opportunities to substitute algorithms.

## Prepared oracle evidence

The [oracle corpus](../tests/oracle/README.md) supplies original probe programs, explicit CLI/input cases, exact output bytes, exit statuses, provenance hashes, and a dependency-free regeneration/check runner. It exercises arithmetic and register boundaries, memory/directives, macro/include/pseudo assembly, branch settings, console syscalls, floating-point bits/printing, seeded randomness, heap alignment, program arguments, entry-point selection, error diagnostics, exit status, and bounded execution. The checked-in Java implementation generates every expected result through the isolated wrapper.

`node tests/oracle/run.mjs --check` is the intended legacy gate integration; it rebuilds the oracle before comparing all cases. It does not require npm or a TypeScript implementation. P2 must run these same inputs through the translated engine and compare the same byte streams and statuses, with the documented checkout-path normalization. Oracle self-reproducibility alone is not evidence of TypeScript parity.

Still untested are exhaustive basic/pseudo instruction variants, NaN payload and special float formatting cases, CP0 exception-handler entry, backstep state and access notification order, multi-file project mode, self-modifying code, memory configurations, dump formats, virtual file operations, dialogs/audio, and tool behavior. Add direct tests or further oracle probes when translating each corresponding Java class. No behavior divergence is proposed by this analysis. Ported source and copied data retain the original authors' copyright and MIT notice from [MARSlicense.txt](../MARSlicense.txt); these newly authored probes and analysis do not copy Java implementation text.
