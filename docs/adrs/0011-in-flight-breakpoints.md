# ADR 0011: Breakpoint changes during Go and the maximum-speed lock

- **Status**: Accepted
- **Date**: 2026-10-23

## Context

Legacy MARS hands the simulator a sorted breakpoint array only when Go starts ([RunGoAction.java](../../_legacy-app/mars/venus/RunGoAction.java) calls `TextSegmentWindow.getSortedBreakPointsArray()`), and `SimThread` keeps that array for the whole run. Its Run menu disables Toggle Breakpoints while running ([VenusUI.java](../../_legacy-app/mars/venus/VenusUI.java) `setMenuStateRunning`). A breakpoint checkbox clicked during unlimited or timed execution changes the table but not the running simulation. The original author describes "instant" recognition of breakpoint changes during a run as desirable but deferred it from release 3.8 because of thread synchronization ([TextSegmentWindow.java](../../_legacy-app/mars/venus/TextSegmentWindow.java), `CheckBoxTableCellRenderer`). MARS-ts previously went further and disabled the breakpoint checkboxes and both breakpoint toolbar actions during execution.

The requested change lets users set, clear, suspend, and restore breakpoints while a program runs, for example to stop a timed loop at a chosen instruction without pausing first. The browser's cooperative scheduler ([ADR 0004](0004-cooperative-simulation.md)) runs the simulator and UI on one thread, so the synchronization concern behind the legacy deferral does not arise: the UI can change breakpoints only while the simulator is suspended at a yield or awaiting input.

MARS's run-speed control also separates two kinds of execution, although its UI does not name them. Finite speeds behave like running under a debugger: the display follows each instruction, highlights the PC, and tracks register and memory writes. Unlimited speed behaves like simply running the program: per-instruction display updates are off ([RunSpeedPanel.java](../../_legacy-app/mars/venus/RunSpeedPanel.java) labels it "no interaction"). Java retains its separate Swing event thread; the MARS-ts browser host handles interaction at cooperative yields or suspended input. Breakpoint editing is a debugger workflow and is not meaningful at the plain-run setting; during a run, a change made then could also take effect only after unobserved instructions. MARS-ts 1.0 keeps MARS 4.5's single speed control rather than adding a formal Run/Debug distinction, but it respects this distinction for breakpoint editing.

## Decision

`Simulator.updateBreakpoints` replaces the active execution's breakpoint list with a sorted copy, or with no breakpoints when the list is empty, and does nothing when no execution is active. The loop's existing breakpoint check reads the current list, so a change takes effect at the next instruction boundary: the stop/pause check, then the breakpoint check against the new PC, then the instruction limit, in the canonical order. Normalization at run start uses the same helper, so the initial list and later replacements follow `SimThread.construct`'s sorting and empty-list rules.

`RunController.updateBreakpoints` forwards a change only while a Go it started still owns the simulator. A pending Step ignores the change, so it still completes with its step-limit result rather than reporting a breakpoint, and the next Go reads the current list as before. `SimulationState` sends the active list (the configured addresses, or none when suspended) after every checkbox change, Toggle all breakpoints, and Clear all breakpoints.

At every finite speed, the Text Segment checkboxes, Toggle all breakpoints, and Clear all breakpoints are enabled whether or not a program runs; the actions require at least one breakpoint, and their keyboard shortcuts share that availability. While the run-speed slider is at its unlimited endpoint, `DesktopState.breakpointsFrozen` disables all of them, whether execution is idle, paused, terminated, or running. The current breakpoint list and suspension state are frozen, not cleared: Go still pauses at them, including changes already applied while running at a finite speed, and switching to maximum does not restore a run's initial list. The lock follows the current slider position, so moving the slider below unlimited unlocks the controls immediately, including during a run, and returning to unlimited locks them again. While locked, hovering a breakpoint checkbox's cell or either toolbar action shows a tooltip advising the user to lower the run speed. The checkbox also exposes that advice as its accessible description, and the toolbar tooltip appends it after the action label through the desktop's `disabledReason` capability. To mark the plain-run setting at all times, the run-speed slider's fill uses a distinct, theme-aware color (`--theme-speed-max`) at its unlimited endpoint. Assembly still clears breakpoints and restores them to enabled, and desktop recovery saves them as before. A later change keeps them across a rebuild whose loaded programs have the same filenames, instruction addresses, and binary statements as the previous successful build ([UI-0019](../deviations.md#ui-0019-breakpoints-survive-an-identical-rebuild)), and an optional, initially off Prompt to clear all breakpoints setting can confirm Clear all breakpoints before it applies; a confirmed clear during a finite-speed Go follows the same replacement path ([UI-0014](../deviations.md#ui-0014-live-breakpoint-controls-at-finite-speeds-locked-at-maximum-speed)).

The simulator tests the replacement list after instruction execution and delayed-branch processing, following Stop/Pause and preceding the step limit. A change delivered during a timed or batch yield is used at the next post-instruction breakpoint check; there is no additional check before fetching/executing the instruction already selected by the PC. Adding a breakpoint at that PC during the yield therefore does not stop that instruction from executing on this pass. During pending input, the list applies at the first breakpoint check after the syscall completes. The engine's update API itself has no speed restriction; the maximum-speed lock is a desktop interaction policy.

## Consequences

Breakpoints supplied to Go, every pause and termination reason, and Step behave as before; only an in-flight list replacement extends the legacy engine behavior. At unlimited speed, the UI keeps the current list and suspension state fixed, with controls visibly locked. Unlike MARS 4.5, breakpoints cannot be edited at the default unlimited speed even while stopped; users lower the speed first, and the tooltips say so. If MARS-ts later adds a formal Run/Debug distinction, this lock is the place where the plain-run side is enforced. No oracle parity is claimed for in-flight changes. Simulator and controller unit tests and a browser workflow pin the behavior; the existing oracle fixtures continue to cover breakpoints supplied at the start of a run. The [deviation catalog](../deviations.md) records the UI policy separately from the engine capability.
