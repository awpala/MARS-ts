# ADR 0002: Like-for-like implementation and browser UI adaptations

- **Status**: Accepted
- **Date**: 2026-10-19

## Context

The requested outcome is the full Java-to-TypeScript/SvelteKit port, targeting MARS-ts 1.0. The checked-in Java implementation is canonical regardless of historical version labels; the port's version is independent. The first implementation must preserve the desktop IDE's layout and behavior, rather than redesigning the application or substituting new assembler and simulator logic. This clarifies the [port plan](0000-port-plan.md) and supersedes its original exclusion of Swing look and feel as a visual reference.

## Decision

Translate the existing Java algorithms and class responsibilities directly. Retain corresponding TypeScript class names and public behavior wherever the language and browser permit. Preserve method names where practical; document necessary mappings instead of introducing a parallel domain model. A source defect remains reference behavior unless a separate decision and fixture authorize a divergence.

Necessary adaptations remain explicit: Java process-global mutable state becomes session-owned instances; Java observers become subscriptions with teardown; blocking I/O and execution threads require an injected browser host and an execution model that keeps the page responsive. These changes do not authorize changes to MIPS semantics or replacement algorithms. The execution model is resolved by [ADR 0004](0004-cooperative-simulation.md). [ADR 0012](0012-deviation-baseline.md) and the [deviation catalog](../deviations.md) distinguish observable adaptations and UI differences from behavior-preserving internal restructuring.

Use the Venus desktop UI as the initial visual and functional reference: menu and toolbar order, run-speed control, Edit/Execute tabs, register and coprocessor panes, text/data/label views, and Messages/Run I/O panes. Preserve the initial desktop arrangement and compact presentation; adapt sizing and scrolling to the browser viewport. Svelte components replace Swing rendering, while source mappings retain the original responsibilities.

Launch directly into the main GUI at the root route. Do not port `MarsSplashScreen` or add a splash, welcome, onboarding, or intermediary launch screen. Any necessary initialization status belongs within the main GUI.

The human explicitly excludes command-line integration from the web port. Do not translate `MarsLaunch`, expose a TypeScript CLI, or retain CLI-only web toolbar/menu options. The later [ADR 0009](0009-program-arguments.md) supersedes the original exclusion of program-argument input controls: the Venus argument input and runtime setup are now supported. The Java CLI remains an oracle harness only; TypeScript parity tests invoke engine APIs directly. This scope exclusion does not change instruction or syscall behavior. Prioritize remaining functional parity over pixel-perfect reproduction of Swing styling.

Replace the desktop filesystem with the localStorage source library and working-buffer recovery described in [ADR 0003](0003-browser-file-workflows.md). Open selects library sources in a same-tab dialog; Import uses the system file picker for `.asm` and `.s` files, and Export downloads portable copies that keep a recognized `.asm` or `.s` extension. Application dialogs appear as accessible modals in the current tab, not new browser windows. Browser download and virtual-file-system behavior must be documented when those features are implemented. Convert raster UI assets to corresponding SVGs while preserving their visual meaning. Use the existing [MARS icon](../../_legacy-app/images/mars.ico) as the favicon. Keep the source raster files unchanged as reference material.

The human requests modern debugger iconography for execution controls and a toolbar group immediately before Help for quick preferences. The current [Settings catalog](../../src/lib/venus/utils/commands/settings.ts), including [ADR 0009](0009-program-arguments.md), orders those toolbar toggles as Labels, Args, popup syscall input, hexadecimal addresses, hexadecimal values, and ASCII. Settings lists the same controls in that order except ASCII, which remains available in the toolbar and Data Segment. At the human’s request, the line-number toggle sits at the end of the editing toolbar group alongside undo/redo and clipboard actions. Retain their text as tooltips and show active preferences with a highlighted button background. Shared toolbar and Settings controls use the same state, callbacks, and enablement; line numbers remain a toolbar control. These presentation changes preserve the underlying setting meanings. Additional shortcut and command-access differences are recorded in the [catalog](../deviations.md), rather than claiming that every legacy command surface is unchanged.

The browser assembles the active source and its explicit `.include` dependencies, resolving current open-buffer text before saved library sources. At the human’s request, the earlier “Assemble all open files in editor” UI adaptation is removed and any saved assemble-all preference is reset when the desktop starts. Unrelated open sources are not included automatically; native directory discovery remains excluded. The assembler’s multi-program algorithms and settings remain available internally for canonical engine behavior. The browser regression scenario in `tests/browser/execution.spec.ts` seeds the retired preference, includes unsaved helper source explicitly, and keeps an unrelated invalid source open to verify this boundary.

The human requests synchronized label navigation: clicking a text label or its address reveals and selects both its assembled instruction in Text Segment and its word in the Data Segment `.text` range. The desktop `LabelsWindow.LabelDisplayMouseListener` routes a text address only to Text Segment; this browser extension deliberately updates both tables, preserving the PC and keeping selection independent of memory-write highlighting. The corresponding Labels row shares the selection highlight. Clicking the same label again through either cell clears selection in Labels and the destination tables. Memory paging uses floor division so a label below a dynamic `$gp` or `$sp` base lies in the selected page. The Java `DataSegmentWindow.displayCellForAddress` helper uses truncated division and signed remainders, which can place such a target outside its displayed chunk; the browser data-label scenario covers a stack label at `0x7fffefdc`, just below the row-aligned default `$sp` base `0x7fffefe0`. The label-navigation scenario in [execution.spec.ts](../../tests/browser/execution.spec.ts) exercises paging, compressed scrolling, user text, and kernel text.

The human requests Text Segment PC tracking that holds the opening page through its last fully visible row, then centers subsequent current instructions vertically below the sticky headings, clamping at either end of the table. Assembly and Reset restart the opening-page behavior. This extends the legacy `TextSegmentWindow.highlightStepAtAddress` visibility-only scrolling; the opening/center/final-page scenario in [execution.spec.ts](../../tests/browser/execution.spec.ts) records the requested browser behavior.

Settings separators follow Values displayed in hexadecimal, Clear all outputs on Go, and Self-modifying code. [ADR 0008](0008-clear-outputs-on-go.md) places Clear all outputs on Go immediately after Initialize Program Counter within the same group. Help retains its canonical Help and About MARS entries first, with a separator before the additional article entries.

At the human's request, the Help browser and every standalone Help-menu article, including About, offer Read Online beside Close. This ordinary link opens the selected article's Markdown companion directly on GitHub in a new tab, allowing readers to dismiss Help and continue using the IDE alongside the reference. Both actions remain visible outside scrolling content, and opening the link preserves the dialog and its selected article. The [companions](../../src/lib/help/markdown/README.md) duplicate the current in-app content and are maintained together with it; there is no content-generation pipeline. Markdown uses native data tables and section-based equivalents of HTML layout tables. Links follow `awpala/MARS-ts` on `main`, so online content reflects published repository files rather than unpublished local edits. The [Help scenarios](../../tests/browser/help.spec.ts) cover destinations and independent new-tab navigation; [catalog tests](../../src/lib/help/articles.test.ts) verify companion coverage and code examples.

Editor typography, syntax colors, and runtime table highlighting are editorial build-time presets imported from JSON under `src/lib/editor/` and `src/lib/venus/`. Remove the “Editor ...” and “Highlighting ...” settings dialogs. These presets are bundled into the app, not loaded from localStorage or offered as end-user customization. Supported quick display controls such as line numbers remain user preferences. The requested light/dark toggle also persists as a presentation preference. Light retains the existing preset colors; a bundled complementary dark palette overrides semantic colors without changing typography, highlighting meaning, or machine behavior.

Preserve source attribution in translated modules, copied data, and derived assets. Wholly original browser integration code that contains no substantial copied or translated source need not carry a legacy-source header. Transformation alone does not remove the MIT notice requirement for copied or substantial portions; retain [MARSlicense.txt](../../MARSlicense.txt) and application About credits.

The port remains ordered by the existing milestones. The human has authorized proceeding through the full port, including the P1 scaffold and bundled tools; no additional milestone confirmation is needed. Defer all Tools menu implementations and File → Dump Memory until core assembly, execution, and debugging are implemented, stable, and validated; retain disabled entries meanwhile. Step-through execution, pause/stop, breakpoints, backstep, and register/memory inspection take priority over Tools and dump/export formats. The core prerequisite is now implemented and validated; File → Dump Memory is implemented with all six enabled legacy formats and the browser save workflow from [ADR 0003](0003-browser-file-workflows.md). Tools remain deferred. Environment restrictions still apply. Java offboarding waits for the existing parity and feature-completion evidence.

## Layout

Keep the legacy application isolated under `_legacy-app/`, including generated documentation in `_legacy-app/docs/`, as specified by the [port plan](0000-port-plan.md#5-proposed-layout). The original license remains at the repository root for both applications. All target application implementation lives under `src/` (`/workspace/src` in the devcontainer): framework-free classes under `src/lib/engine/`, GUI components and browser adapters under responsibility-specific `src/lib/` directories, and SvelteKit routes under `src/routes/`. The root `package.json` names the package `mars-ts`, owns dependencies and scripts, and works with the root SvelteKit/TypeScript/Vite configuration to resolve this source tree; the scaffold-declared `#lib/*` subpath maps to `src/lib/*`. Keep one root application package; do not create a second app directory or nest another package inside `src/`.

Reserve `static/` for browser assets, with converted toolbar icons under `static/icons/`. Keep oracle inputs, generated outputs, and their dependency-free regeneration/check runner under `tests/oracle/`; the later Vitest parity suite consumes the same fixtures. These preparatory assets and fixtures may be created before the app scaffold and do not constitute an implemented UI or engine.

## Consequences and validation

Review each translated unit against its named Java source and committed oracle evidence. Do not replace full source behavior with a small instruction subset presented as a complete engine. Browser validation must compare the initial layout and exercise file opening, modal focus/closing, editing, assembly, execution controls, and register/memory updates. SVG conversion and a copied favicon alone do not establish UI parity.

The fixture runner must preserve stdout, stderr, and exit status, record options and stdin, and identify any environment-path normalization. Fixture checks prove the reference corpus is reproducible; only comparisons against the TypeScript engine establish port parity.
