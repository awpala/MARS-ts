# ADR 0017: Portable MARS-ts data and the schemas directory

- **Status**: Accepted
- **Date**: 2026-11-16

## Context

Everything the application keeps lives in one browser profile's localStorage ([ADR 0003](0003-browser-file-workflows.md), [ADR 0007](0007-desktop-session-recovery.md)): the source library, open-buffer backups, display, pane, theme, and engine preferences, and the desktop recovery record. Export File and Export All Files carry source text only. Moving to another browser, profile, machine, or copy of the [standalone HTML](0016-standalone-html-distribution.md), or keeping a backup before clearing site data, therefore lost settings, unsaved buffers, and the loaded program. The repository owner asked for a whole-application export and import whose payload mirrors the current localStorage data, defined by a checked-in schema, with import validated against that definition.

## Decision

**Payload.** Export MARS writes `mars-ts-data.json`: an envelope with the fixed `format` `mars-ts-data`, `version` 1, the schema identifier, and the export time, around a `storage` object that mirrors localStorage. Each property is a storage key and each value is that key's record: parsed JSON for the source library, workspace, display settings, pane layout, and desktop session, and the stored text for the theme and each engine setting. Absent keys are omitted. The payload is a mirror rather than a new project format, so it adds no second representation of sources, settings, or machine state to keep in step with the first.

**Schema.** The payload is defined by [schemas/mars-ts-data.v1.schema.json](../../schemas/mars-ts-data.v1.schema.json), a JSON Schema 2020-12 document. Record objects are closed, so a stored field the schema does not name fails the application's own export and its tests instead of drifting. The application imports the checked-in document and evaluates it, deriving the mirrored key list and each key's text-or-JSON encoding from it; the schema is not restated in TypeScript. A small evaluator for the keyword subset the schemas use lives in the [browser data adapter](../../src/lib/browser/data/README.md) and refuses any keyword it does not implement. No validator dependency is added, consistent with the hand-written ZIP codec of ADR 0003.

**The `schemas/` directory.** A new top-level [schemas/](../../schemas/README.md) directory owns these definitions. It is named in the plural and documented as the general home for schema-aware, bounded payloads that cross a boundary of the system or pass between its parts, so later payloads follow the same conventions: one file per payload version, a `main`-branch URL as `$id`, a self-identifying `format` and `version`, closed records, and the supported keyword subset. It holds only the MARS-ts data schema now; a schema is added when the application reads or writes its payload. The package gains a `#schemas/*` subpath import, and the browser-test and standalone builds copy the directory with the sources.

**Validation.** A selected file is parsed and checked in two gates: the schema, then, for a conforming payload, the reader that owns each record (source and workspace name rules and uniqueness, the display and pane loaders, and the recovery record's validator). At most twenty problems are reported with the JSON Pointer of each failing value. Files above 32 MiB are rejected unread. Export MARS applies the same check to its own capture and exports nothing when stored data does not conform.

**Import MARS replaces, then restarts.** Every read file opens an Import MARS data dialog. A conforming file shows what it contains (saved sources, open files and how many are unsaved, settings records, the session and its loaded program, the export time) and states that the saved sources, open files, settings, and session now in the browser will be removed, including how many open files have unsaved changes; a rejected file lists its problems with Import unavailable. Nothing is stored until confirmation. Confirming suspends the desktop's recovery writer, replaces every mirrored key in one pass (keys the file omits are removed; keys outside the schema are untouched), and reloads the application so each owner restores from the new records through its existing startup path. A failed write restores every previous value, resumes recovery, and stays in the dialog. Merging was rejected: it would need conflict rules across every record, where replacement is exact and the dialog can state it plainly.

**Commands and placement.** Import MARS ... and Export MARS are File commands with toolbar buttons directly after Export All Files, before Dump Memory. Both are unavailable while a program runs. The source-file commands are relabeled to keep the two pairs apart: Import becomes Import File(s) ..., Export becomes Export File, and Export All becomes Export All Files; their command identifiers, icons, and behavior are unchanged, and Import File(s) gains the Ctrl+I shortcut (Meta accepted), captured app-wide like the other command shortcuts. Import File(s) moves to directly before Open, and the File menu lists its commands in toolbar order, adding only the text-only Close and Save All; this amends the labels and placement recorded in ADR 0003. The transfers reuse the existing picker status, save picker, and download-link lifecycle. Their original glyphs are one rocket: lifting off from a surface line with paired ascent arrows for Export MARS, and mirrored nose-down with paired descent arrows for Import MARS.

## Consequences and validation

Export MARS gives a complete portable copy, and the standalone distribution's storage limits now have a transport for more than sources. The schema must change with any stored record, which the closed records and tests enforce. Only version 1 is read and there is no migration; an incompatible change is a new schema version. Import MARS discards the receiving browser's data by design and requires an explicit confirmation. Other open tabs of the same origin continue to write their own state, as before.

Unit tests cover the evaluator's keywords, limits, and refusal of unsupported schemas; that the schema's keys, vocabularies, field sets, and array sizes equal those of the record owners; capture of records written by the application's real writers, including a stepped program's checkpoint; rejection paths with their pointers; the owners' rules; file reading; and replacement with rollback. Browser scenarios cover the exported file against live storage, import into a separate browser profile with confirmation, cancellation, restart, and the restored sources, draft, settings, theme, and paused program, rejection of nonconforming files, and availability while running. [UI-P0010](../deviations.md#ui-p0010-portable-application-data) records the adaptation. Native file dialogs are represented by Playwright's chooser and download events; other browsers and quota exhaustion in a real profile remain unvalidated.
