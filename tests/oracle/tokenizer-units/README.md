# Tokenizer Java oracle

This probe exercises the unmodified `_legacy-app/mars/assembler/Tokenizer.java` through its line, instruction-example, and whole-program entry points. It captures token types and values, one-based source positions, original/current program references, processed source text, include source maps, exact diagnostic fields, and failure categories. The fixtures include comments and delimiters, signed operands and exponents, string termination and escapes, UTF-16 character literals and octal escapes, macro syntax, `.eqv` substitution/redefinition/errors, nested includes, duplicate and recursive includes, missing files, and errors in included files.

Run `build-legacy` once, then `node tests/oracle/tokenizer-units/run.mjs` to regenerate or `node tests/oracle/tokenizer-units/run.mjs --check` to compare. The shared [probe runner](../units/run.mjs) rejects stale jars and non-JDK-21 toolchains, compiles the probe outside the legacy tree, isolates Java Preferences, and records exact streams, exit status, source hashes, and the invocation in `golden.json`. The source programs under `inputs/` are original test inputs; the Java implementation remains read-only. Never edit golden output manually.

The [Vitest comparison](../../assembler-tokenizer.test.ts) supplies in-memory program/source contracts and uses the real ported register classes. Operator names come from the Java instruction set captured by this probe; production instruction lookup remains injected into the tokenizer. This establishes tokenizer behavior without introducing an alternate assembler or claiming instruction execution is complete. Whole-program tests use real fixture files only in the Node test adapter; the engine performs no platform I/O.

Several surprising Java behaviors are preserved: whitespace-only lines retain their text while empty lines return an empty list immediately; `.eqv` definition source-map entries become empty because the directive returns before setting processed text; duplicate include paths are rejected as recursive even without an active cycle; missing parent paths concatenate the text `null`; unterminated strings remain quoted-string tokens for the assembler to diagnose; and errors on a tokenizer persist between calls. Standalone `.eqv` definitions require dictionary initialization through `tokenize`, just as in Java. Java null and string-bounds failures map to TypeScript `TypeError` and `RangeError`; tests compare the corresponding failure category, while ordinary MARS diagnostics match exactly.

The same test exhaustively checks Java letter/digit classifications for all 65,536 UTF-16 code units against the [generated JDK character table](../highlighting/character-data.json). Character categories are shared by engine tokenization and editor highlighting so browser Unicode-version differences cannot alter lexical behavior. Regenerate that table with the [highlighting probe](../highlighting/run.mjs); its check also validates the generated engine copy.
