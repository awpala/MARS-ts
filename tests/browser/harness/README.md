# Browser test harness

This directory owns infrastructure shared by the semantic browser groups: suite discovery, snapshot-runner orchestration, project logging, desktop readiness and startup setup, browser API stubs, source-record seeding, domain locators, and independent ZIP archive inspection. Helpers observe or mount the production desktop and leave workspace and machine policy with their existing owners.

The command wrapper collects the requested cases before starting independent group processes. The application, browser tests/helpers, and configuration are frozen once under `__build/browser-runs/<run-id>/inputs`; each queued group copies that baseline into its private `__build/browser-runs/<run-id>/<group>/app`, links read-only installed dependencies, owns its generated/cache output and an available server port starting at 6278, and writes root-owned results under `__build/browser-results/<run-id>/<group>`. Root-owned log/report destinations are injected into each child, keeping evidence outside the snapshot. The runner captures complete child stdout/stderr logs and continues independent groups after a failure. Inventory-only listing starts no snapshots or browser sessions.

Each group runs its own startup check against its captured application. Readiness uses the desktop controls hook and explicit busy state, then confirms New is enabled. Browser operations and seeded records remain local to each scenario's context; setup does not supply a shared application session. Archive inspection uses the system `unzip` tool to validate downloaded entries independently of the exporter.

Node-only discovery finds semantic subdirectories containing recursive `.spec.ts` files and supplies both local projects and the CI matrix, rejecting loose root specs and reserved/invalid group names. The additive reporter writes live per-project/startup/infrastructure logs with outcomes, errors, worker output, and completed/unrun summaries. It preserves console reporting and fails validation if logs cannot be written; listing scenarios creates no project logs. The master invocation log captures output outside reporter events.

Add a helper here when multiple semantic groups need the same test setup or observation contract; keep feature assertions and fixtures with their owning group. The [suite guide](../README.md) owns selector conventions, run commands, logging, and evidence limits. This infrastructure is test-only and is not imported by application entry points.

Working-tree edits do not update active or queued groups from that invocation; validate them with a fresh affected-group invocation. Application, test, harness, and configuration files are all captured; keep those snapshots and the shared read-only installed dependencies unchanged. This lets authorized fixes continue while unaffected snapshots finish.
