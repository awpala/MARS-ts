# Desktop contexts

This module provides both the per-instance desktop state and a narrow command capability shared by independently composed menus and toolbars. [VenusUI.svelte](../VenusUI.svelte) constructs the state and installs both contexts during component initialization. Descendants read them during their own initialization; reading without a provider throws through Svelte's typed context accessor.

The command capability exposes dispatch and functions that read current enablement and pressed state, and it also exposes the live toggles menus and toolbars render: `displayToggles()` returns the preference toggles shared by the toolbar and the Settings menu, and `engineToggles()` returns the engine-setting checkboxes that only the Settings menu offers. Each toggle carries its label, description, current value, whether execution blocks it, and the request to invert it. These functions observe the desktop's live reactive values rather than snapshots captured at registration. Dispatch keeps file operations, execution coordination, and menu dismissal with the session owner, and the toggles are built from the [Settings catalog](../utils/commands/README.md) by the desktop coordinator. The installer wires the capability to the coordinator when it provides the desktop. This narrow capability does not expose a mutable machine or editor or transfer their ownership to consumers; it is also why the shell (MenuBar and Toolbar) never needs the full desktop context.

Only the accessor pair is module-scoped. Every rendered desktop supplies its own capability, including during SSR. There are no subscriptions, timers, or resources in this context to release; the root still owns machine/controller teardown. Generic panes, dropdowns, and buttons accept props and snippets without requiring this context, so they can be composed independently. Add another context only for a distinct capability shared across a component subtree; keep local tab, pointer, and input state with its existing owner.

Components that coordinate with a desktop owner read the full desktop context to reach the responsible workspace, search, simulation, or preference owner: dialogs, file-transfer behaviors, desktop keyboard bindings, the debugger views (messages, the Execute pane and its panes, and the register banks), and the editor views (source tabs and the source editor). Reading the context lets these views follow live owner fields and call owner methods instead of receiving each value, callback, and preference through a chain of props. Generic panes, tab strips, dropdowns, buttons, and feedback remain props/snippet driven, so they stay reusable and testable without a provider; the shell reads only the command capability. File-transfer components register their browser action with that desktop and remove only their own registration during teardown.
