# Debugger and console views

This group presents assembled statements, data memory, symbols, register banks, execution location, and message/console output. The [simulation owner](../../state/README.md) and framework-free [RunController](../../RunController.ts) retain execution state and scheduling. Components consume public hardware APIs and controller snapshots; manual edits go through existing hardware contracts and then ask the simulation owner to refresh. These views coordinate with several desktop owners, so they read the display preferences, simulation state, and workspace through the [desktop context](../../context/README.md), as the dialogs and transfer components do, instead of receiving each persisted value as a prop. Only the execution handles remain props: [ExecutePane](ExecutePane.svelte) receives the mounted machine, controller, and snapshot from VenusUI, whose guard guarantees they exist, and [RegisterBanksPane](RegisterBanksPane.svelte) receives its register handles, refresh sequence, controller, and an ID for its resize separator. Everything else the views read or change (the selected register bank, label selection, Data Segment range and page, display bases, label filters and sort state, breakpoints, the argument draft, the Data Segment height, console text, and pending input) lives in the owners. Generic controls, layout, and feedback components stay prop-driven and never read the context, so they remain usable outside the desktop.

[ExecutePane](ExecutePane.svelte) composes the Execute view from three panes inside the shared [SegmentPane](SegmentPane.svelte) frame, a bordered pane with a themed heading band and optional trailing actions: [TextSegmentPane](TextSegmentPane.svelte), [LabelsPane](LabelsPane.svelte), and [DataSegmentPane](DataSegmentPane.svelte). Each ports the view of its legacy window (`TextSegmentWindow.java`, `LabelsWindow.java`, and `DataSegmentWindow.java`) within the arrangement of `ExecutePane.java`. The legacy windows reach into one another for label navigation, address and word formatting, memory display, and write following; the port keeps that cross-window behavior in one model, [ExecuteView](ExecuteView.svelte.ts), created once per mounted Execute pane and installed for the three panes through its own context (`setExecuteView` and `getExecuteView`; reading without a provider throws). The model owns navigation between labels, instructions, and memory words, which chooses the Data Segment range and page and reveals and focuses the destination; address and word formatting in the selected bases; display-only memory reads and manual word edits, with the failure text of a refused edit; revealing the selected label when Execute opens or a session is restored; and write observation. `observeWrites` follows observed stores with the highlight, the matching page, and a scroll to the word, and returns the teardown of its simulator and memory subscriptions for the effect that starts it; `resetObservation` clears write highlighting and re-captures the instruction words after Assemble or Reset replace the statements, as the legacy run actions call `clearHighlighting()`. The model is constructed from an `ExecuteSource` (the DOM ID prefix ExecutePane generates, and the machine, controller, and snapshot it receives) plus the desktop's display and simulation owners. Those owners keep every persisted value (label selection, Data Segment range and page, display bases, label filters and sort state, the argument draft, and the Data Segment height); the model reads and writes them there directly and holds only transient highlight state and values derived from the machine, and after a manual memory edit it asks the simulation owner to refresh. TextSegmentPane and LabelsPane take no props, and DataSegmentPane takes only the Execute view's measured height, each reading the Execute view model and the owners it needs, so VenusUI's contract with the Execute view is just the machine, controller, and snapshot.

The Labels pane's Close icon button hides it by clearing the display owner's persisted Show Labels Window preference, which clears that toggle in both the toolbar and Settings. Its close affordance shares the source tabs' themed hover styling and tooltip through CloseButton.

The Labels view preserves the engine's symbol-table ownership: the global table appears under `(global)`, followed by program-local tables headed by their source basenames. These full-width group headings are centered. Filtering and sorting operate within each group, and source filenames come from assembled programs. Rendering does not merge or mutate the underlying tables. The selected Labels row is highlighted in tandem with its segment destinations. Both the Label and Address cells expose the desktop navigation tooltip and activate the same destination: text labels select and reveal both their assembled instruction and the corresponding word in the Data Segment `.text` range, with keyboard focus on the instruction; data labels choose the nearest legacy range, restore the page containing the address, and center and focus its word cell, including the containing word for byte labels. The simulation owner retains the selected label identity across Edit/Execute remounts and localStorage recovery with the loaded program; filename, case-sensitive name, and address distinguish local/global symbols and aliases. Restoring Execute reveals selected rows without changing keyboard focus. Clicking the same label again through either cell clears selection in Labels and the destination tables; distinct labels retain their own row selection even when they share an address or occupy one word. Navigation restores visibility even after paging or compressing and scrolling the Data Segment, and does not change the PC. Register Name entries use a pointer cursor and expose the descriptions from the corresponding legacy integer, exception, and floating-point register windows through the shared themed tooltip; those texts are held by [registerDescriptions.ts](registerDescriptions.ts), keyed by register bank, beside the register pane that displays them.

Register and execution views release their subscriptions with their component lifetime. Register and memory write following reads the run controller's `isObservingWrites()` flag, which it sets from each simulator notice, instead of each pane tracking start notices itself, so opening Execute during a stepped or timed run follows writes immediately. The Data Segment's highlight latch is the one start-notice handler: the simulator notifies observers in reverse registration order, so a start notice reaches a pane's handler before the controller has updated its flag, and the handler classifies the notice itself with the shared `observesWrites` rule. Assembly and Reset clear Data Segment write highlighting after data initialization, as the legacy run actions do; assembly writes are not left highlighted. Single-step and timed execution observe runtime writes; unlimited Go does not introduce new write highlights. Observed stores and backstep writes reveal their destination range/page and center its word without selecting a label or moving keyboard focus. Manual data-memory edits update values without introducing an execution highlight. Changed assembled text words retain the legacy self-modifying-code exception: even manual Code edits and unlimited execution reveal the changed word in Data Segment. Backstep preserves the undone instruction's delay-slot display context. Assembly and Reset restore the first `.data` page, and paging clamps to the legacy user/kernel address boundaries. Register banks retain independent last-write highlights, select the bank receiving a stepped/timed or backstep write, and clear all highlights on assembly/reset. Completion retains the last executed instruction highlight until backstep, assembly, or Reset changes the execution location; errors retain the faulting instruction. The exact stop address is saved in the browser checkpoint and restored without guessing from the next PC. The controller captures the executed address from simulator stop notices, so a terminating syscall or a jump off text does not highlight an unexecuted following row. Numeric cell formatting, the Data Segment range and paging rules, the Labels sort states, and the console's Clear/Clear All labels, shortcut hints, and derived `aria-keyshortcuts` values are shared through the [presentation utilities](../../utils/README.md); the views keep rendering, focus, and subscriptions. The console view renders inline input and reports submission or Stop; simulation state retains the pending syscall resolver, echo rules, and cancellation.

Sized regions come from [layout](../layout/README.md): Text Segment, Labels, and Data Segment reach Pane through SegmentPane, while Register Banks and Messages compose it through TabbedPane, whose tab type follows the closed register-bank and message-tab vocabularies of the session adapter. Debugger views retain their headings, column header cells, table bodies, scrolling, and content selection. The Text Segment and Labels keep their pane heading, any filter controls, and sticky column headings fixed while only their table rows scroll. PC tracking holds the opening page through its last fully visible instruction, then centers each current row below the column headings, with native scroll limits pinning the first and last pages. Assembly and Reset restart this opening-page behavior; tracking preserves horizontal position and keyboard focus. A layout divider between the Text Segment row and Data Segment sets the display owner's persisted Data Segment height; when compressed, only the address rows scroll, under sticky column headings. Opening the range selector selects a hidden placeholder bearing the current label, because native selects report no change for a reselected option; choosing the current range therefore resets it to its first page. Shared [controls](../controls/README.md) supply action buttons, including the Data Segment's paging and restore icon buttons (whose transparent resting border shows the accent border on hover, like toolbar buttons) and console Clear/Clear All and input actions (the outlined Button variant), labeled display and label-filter checkboxes, and the condition-flag group. The register view interprets condition bits and writes the one flag a click changes, even during execution, as the legacy checkbox listener does; MultiSelect only renders and reports selection state. Breakpoint cells keep individually named native checkboxes, centered in their cells, without accompanying visible text. Descriptions use [feedback](../feedback/README.md), whose InlineAlert presents the register pane's and the Data Segment's edit failures beneath their controls in the themed error color; the owning component keeps the message and decides when it clears.

[MachineTable](MachineTable.svelte) is the shared frame for the Text Segment, Labels, Data Segment, and Registers/Coproc 1/Coproc 0 tables. It renders the `<table>` root with one sticky heading row, alternating stripes, borders, cell padding, line height, and the bundled highlighting preset, which no other component imports. Callers supply the header cells and `<tbody>` sections and mark highlight roles with `data-highlight`: `pc` and `delay-slot` on Text Segment rows, `memory` on the edited Data Segment word, and `register` on the last-written register row. Label navigation separately sets `data-selected="true"` on the selected Labels row, destination instruction row, and memory word; this selection remains visible across the tables when focus moves and does not represent a machine write. Callers also mark body cells with three table-owned roles: `numeric` right-aligns monospace numbers and hexadecimal words so they compare digit by digit, `identifier` bolds the cell naming its row (row addresses are both, while labels and register names are bold but stay left-aligned), and `action` marks a cell whose only content is one action button, moving the cell's padding into the button so the whole cell is that button's hover, focus, and click target. The Text Segment's Source column uses `action` for every row with a source link, whose tooltip reads "See in source file"; a row whose instruction was modified by self-modifying code shows an inert `------` instead and is not an action cell. The Labels table uses it for both its label-name and address buttons, so hovering or clicking anywhere in either cell, including the empty side of a short name or a right-aligned address, selects the label. The table applies the preset's data and register enablement flags. Cells draw separate borders, right and bottom plus the first cell's left edge and each heading's top edge, so the sticky heading row carries its own border and scrolled rows never show through above it. It has no wrapper element, so scroll containers stay with callers, and callers must not pass CSS custom-property attributes, which would insert one; a bindable rendered height supports Data Segment geometry. Every caller uses the defaults: application-font headings, as in the legacy JTable headers, above monospace preset cells with `2px 4px` padding, normal line height, and one light-theme border fallback. [CellInput](CellInput.svelte) is the borderless value input that fills its cell and inherits the cell's text alignment, with a minimum width that keeps a hexadecimal word visible. Enter commits by blurring, so the owner's native change handler still validates, writes, and reformats the value; Text Segment code, Data Segment words, integer and Coproc 0 registers, and Coproc 1 float/double values use it.

[RegisterBanksPane](RegisterBanksPane.svelte) groups the Registers, Coproc 1, and Coproc 0 tabs in the sidebar controlled by the Register Banks switch. Its name distinguishes the containing pane from the Registers tab. These views compose legacy ExecutePane, TextSegmentWindow, DataSegmentWindow, LabelsWindow, RegistersPane and its register windows, and MessagesPane responsibilities; the Text Segment, Labels, and Data Segment windows each map to a pane, and their shared navigation maps to the Execute view model. The [Venus guide](../../README.md) documents supported debugging and browser adaptations. Add machine-inspection or execution-output presentation here; keep engine algorithms and simulation lifetime outside components.

The optional Program Arguments row is new content between the Text Segment heading and its table header, outside the scrolling table. Its draft belongs to the simulation owner, which the pane edits directly, persists across pane remounts and reloads, and uses the legacy runtime-argument tooltip. Settings and the adjacent-to-Labels Args toolbar toggle share its visibility; RunController owns when the draft becomes machine arguments.
