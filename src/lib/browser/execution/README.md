# Browser execution services

This directory owns the per-machine browser services that execution reaches through engine host interfaces: the cooperative scheduler that yields to the event loop, and the Web Audio tone host for MIDI services 31 and 33. [Simulation state](../../venus/state/README.md) constructs one of each with its machine, supplies them to the engine through the machine's host, releases their waits from the simulator's stop listener, and disposes them on teardown. Each instance owns its browser resources (MessageChannel ports and timers for the scheduler; an audio context, voices, and wait timers for the tone host), and nothing lives in module scope. The tone host imports only the engine's `Tone` and `ToneGeneratorHost` types and the scheduler imports nothing; the engine never imports this directory, and its instruction batching, check order, and MIDI argument validation remain engine contracts.

[CooperativeScheduler](CooperativeScheduler.ts) belongs to one browser machine and is constructed by simulation state during browser initialization. Zero-delay yields post MessageChannel tasks; finite-speed waits use timers with the requested delay. Pause and Stop release current waits. Disposal settles waits, cancels timers, removes the message handler, and closes both ports synchronously. Unique task tokens keep messages queued before a wake from settling a later wait. The engine retains its 1,000-instruction batching and instruction/check order; no scheduler resource lives in module scope.

[WebAudioToneHost](WebAudioToneHost.ts) implements the engine's `ToneGeneratorHost` for MIDI services 31 and 33. Each desktop machine owns one instance: [SimulationState](../../venus/state/SimulationState.svelte.ts) constructs it with the machine, releases its waits from the simulator's stop listener, and disposes it on teardown. The host creates its `AudioContext` only when first needed, and Go and Step call `prepare()` synchronously within their user gesture so browser autoplay policy lets the context start or resume there. Every tone is one sine oscillator at 440 · 2^((pitch − 69) / 12) Hz; the instrument number has no audible effect. Gain peaks at 0.2 · (volume / 127)² with a fade-in of 5 ms or half the duration, whichever is shorter, and a 30 ms fade-out after the duration; volume 0 and duration 0 create no voice. The host tracks up to 32 voices; starting another removes the oldest from that set and fades it out over 30 ms, so its fading tail can overlap the replacement. After two seconds without a sounding voice the context is suspended and resumed for the next tone. Only synchronous tones request a duration wait; asynchronous tones allocate no waiter. A synchronous tone's wait is a timer at its duration, independent of the audio graph, so MidiOutSync keeps its timing when Web Audio is missing, blocked, or refuses a context. `release()` resolves every pending wait without silencing sounding tones, which continue to their scheduled end as in Java; `dispose()` releases waits, stops every voice, closes the context, and makes later tones silent and immediate. [ADR 0015](../../../../docs/adrs/0015-midi-web-audio-tones.md) records these choices.

Add a host implementation here when its engine interface exists and it owns a browser resource for the lifetime of one machine. Storage-backed engine preferences belong to [preferences](../preferences/README.md); console input, syscall dialogs, and entropy are supplied by simulation state itself.
